# История обновлений РМК

Формат версии: **MAJOR.MINOR.PATCH**
- **MAJOR** — крупная переработка / несовместимые изменения
- **MINOR** — новые функции (обратная совместимость сохранена)
- **PATCH** — исправления и мелкие правки

Источник истины версии — константа `RMK_VERSION` в `admin-rmk.js`.
При каждом обновлении: поднять `RMK_VERSION`, добавить запись в `RMK_CHANGELOG` (в том же файле), продублировать сюда и обновить дефолт `rmkVersion` в `1c-sync-barcodes/api/backup.js`, а также кэш-бастинг `?v=` ассетов в `admin-rmk.html`.

## v1.2.41 — 15.08.2026 — Фикс: разные товары сливались в одну строку чека (касса кассира)

- Касса кассира: два разных экземплярных товара могли попасть в ОДНУ позицию чека (напр. обувь р-40 и коврик).
- Причина: позиции группировались по характеристике (charC1Ref), а у нативных товаров она пустая (null), поэтому `null === null` сливал их все.
- Теперь группировка строго по `variant_id` (точный ключ варианта товара) — разные товары больше не путаются. Если `variant_id` нет — каждый скан отдельной строкой.
- Backend (`scanProduct`, `findBySuffix`) теперь отдаёт `variantId` при скане.
- На списание и цены баг не влиял задним числом — чек всегда списывал конкретные отсканированные штрихкоды (`uniqueBarcodes`), но цена позиции могла отображаться от первого товара — теперь исправлено.

## v1.2.40 — 14.08.2026 — Выручка и Статистика — из локальной кассы (без 1С)

- Раздел «Статистика» (`action=stats`) теперь считает выручку, чеки, топ-магазины/продавцы/товары из локальной кассы (`pos_receipts`/`pos_receipt_items`), а не из 1С.
- Топ-товары больше не ограничены 150 чеками — состав чека берётся из базы, без поштучных запросов в 1С.
- Раздел «Выручка-Расходы» (`action=fin-profit`): выручка и прибыль по магазинам — из локальной кассы (`finNetBySalonName` читает `pos_receipts`), а не из агрегата 1С (`sales_daily_1c`).
- Себестоимость (COGS 50%), расходы, зарплаты и расчёт чистой прибыли не изменились — поменялся только источник выручки.
- Сопоставление салонов — по нормализованному имени магазина (`shop_name`), т.к. `shop_wh_id` в чеках не заполнен.
- Важно: локальная касса хранит чеки с июня 2026 — за более ранние периоды выручка показывается пустой.

## v1.2.39 — 13.08.2026 — Фикс сверки перемещения для native-товаров

- **Симптом:** при перемещении native-товара (созданного в РМК, без 1С) экран сверки показывал «Совпадают (найдены в 1С): 0 / Не найдены: 1», хотя товар реально есть в базе.
- **Причина:** `trCheckHTML` считала товар найденным только по `productC1Ref` (ссылка на 1С). У native-товаров `c1_ref`/`c1_prod_ref = NULL`, поэтому они всегда попадали в «Не найдены».
- **Фикс:** найденным считается экземпляр с `productC1Ref` ИЛИ с реальным штрихкодом (в `TR.items` попадают только экземпляры, найденные бэком). Строка переименована в «Найдены» с счётчиком native.
- **Важно:** само перемещение native-товаров работало и до фикса (`transfer-create` берёт позицию по штрихкоду, `moveUnitLocal` добирает товар/размер из `stock_units`) — правка чисто косметическая.

## v1.2.37 — 13.08.2026 — Фикс рассинхрона номенклатуры при перепроведении поступления

- **Симптом:** один и тот же штрихкод в перемещении принадлежал одной номенклатуре, а при печати из поступления — другой (ПОСТ-2026-0013 / RMK-000042).
- **Причина:** в ветке перепроведения `1c-sync-barcodes/api/pos.js` экземпляры фильтровались только по размеру, без учёта `product_id`. При многострочном поступлении с общими размерами последняя строка забирала все экземпляры размера — модели слипались в один товар.
- **Фикс (`api/pos.js`):** привязка экземпляра к строке теперь через `product_id` его текущего варианта (`unitVarProd`), а не только по размеру. Печать ШК берёт имя товара по фактической модели экземпляра.
- **Данные:** 30 экземпляров ПОСТ-2026-0013 восстановлены по правильным моделям (по 15 на 3349-5A / 3349-5C / 3349-2B), остатки пересчитаны.
- **Фронт:** поведение не менялось — только `RMK_VERSION` → 1.2.37 и запись в истории изменений.

## v1.2.35 — 12.08.2026 — Перемещение: вариант целевого склада по размеру экземпляра (фикс нативных товаров)

- **Задача:** сквозной тест (приход на Основной → перемещение на Интернет-магазин) вскрыл: на складе-получателе вместо трёх вариантов (40/41) появлялся ОДИН вариант-«40» со stock=3 — экземпляр 41-го размера привязался к варианту-«40».
- **Корневая причина** (`1c-sync-barcodes/api/pos.js`, `ensureVariantForWarehouse`): поиск варианта целевого склада шёл по (`product_id` + `c1_char_ref`). У нативных товаров (без 1С) `c1_char_ref` пуст (NULL), а `NULL = NULL` давало ложное совпадение с первым созданным вариантом → все размеры слеплялись в него. Фолбэк по размеру не срабатывал, т.к. первый шаг уже возвращал «совпадение».
- **Фикс:**
  - `ensureVariantForWarehouse` теперь принимает размер ПЕРЕМЕЩАЕМОГО ЭКЗЕМПЛЯРА (`su.size_label`) и ищет/создаёт вариант по ЭТОМУ размеру, а не по размеру «чужого» исходного варианта.
  - `c1_char_ref` участвует в поиске ТОЛЬКО когда реально заполнен (не NULL) и как доп-условие к размеру.
  - `moveUnitLocal` передаёт `u.size_label` в `ensureVariantForWarehouse`.
- **Проверено** сквозным тестом на проде с полным откатом: после перемещения на складе-получателе создаются отдельные варианты на каждый размер, остатки = факт.
- **Важно для SaaS-каталога:** нативные товары без 1С — основной сценарий будущего продукта; баг бил именно по ним.

## v1.2.34 — 12.08.2026 — Матрица «Поиск товара»: раскладка по факту экземпляров

- **Задача:** после починки остатков (v1.2.33) матрица «Поиск товара» всё равно показывала неверное распределение по клеткам склад×размер (напр. Айни×43 = 10, хотя на Айни по 2 шт каждого размера).
- **Корневая причина:** обработчик `product-detail` строил клетку матрицы по атрибутам ВАРИАНТА (`product_variants.size_label` + `warehouse_id`). Часть экземпляров привязана к варианту с чужим размером (артефакт рассинхрона 1С): экземпляр 40-го размера, «висящий» на варианте-«43», показывался в клетке 43. Отсюда «кучи» в одной клетке при верном итоге.
- **Фикс на бэкенде** (`1c-sync-barcodes/api/pos.js`):
  - `productDetail` теперь строит матрицу по СКЛАДУ И РАЗМЕРУ ЭКЗЕМПЛЯРА (`stock_units.warehouse_id` + `stock_units.size_label`) — единственный источник правды. Вариант используется только для цены и `variantId` при клике по ячейке.
  - `variantUnits` (панель кодов по клику) принимает `warehouse_id` и `size` и фильтрует экземпляры по клетке — число кодов совпадает с количеством в ячейке.
- **Фикс в БД** (RPC `stock_matrix`): группировка по одному нормализованному размеру (убран `pv.size_label` из `GROUP BY`), чтобы не было дублей клеток. Эта функция матрицу «Поиск товара» не питает, но используется в других местах.
- **Данные не менялись** — исправлено только отображение. Рассинхрон привязки экземпляров к вариантам с чужим размером остаётся в данных (тема отдельной чистки).

## v1.2.33 — 11.08.2026 — Остатки вариантов: надёжный пересчёт при перемещениях

- **Задача:** после проведения перемещений (RMK-000040/041/042) экземпляры сели правильно, но агрегат `product_variants.stock` остался старым — в каталоге остатки по складам врали.
- **Корневая причина:** `recalcVariantStock` был обёрнут в немой `try/catch(_){}` и мог молча упасть; при проведении строки с `moved=true` пропускались, а вместе с ними — и пересчёт.
- **Фикс на бэкенде** (`1c-sync-barcodes/api/pos.js`):
  - `recalcVariantStock` больше не проглатывает ошибки: логирует и возвращает статус.
  - `transferDocPost`/`transferDocUnpost` после проведения/отката принудительно пересчитывают остаток ВСЕХ вариантов документа (целевых и исходных), независимо от `moved`.
  - Новый action `recalc-variant-stock` — массовый пересчёт по факту: `{all:true}` / `{productIds:[]}` / `{warehouseId}` / `{variantIds:[]}`.
- **Данные исправлены** вручную: 31 вариант приведён к факту (бэкап сохранён, 0 расхождений после).
- Матрица «Поиск товара» (RPC `stock_matrix`) считает по факту экземпляров и верна всегда — не изменена.

- **Задача:** разрешить перемещение любого экземпляра независимо от того, на каком складе он числится и какой у него статус (в т.ч. проданный / списанный).

  - в отчёте остатков (`productSearch`, `productDetail` в `api/pos.js`) отрицательный `stock` теперь считается как 0 (`Math.max(0, stock)`);
  - разово выровнены 79 вариантов с минусовым остатком в БД (все — товары из 1С, `stock` → 0).
- **Примечание:** матрица-детализация товара уже считала по реальным экземплярам `stock_units` — поэтому «Итого по размеру» было верным, а в минус уходила только агрегация по `stock`.

## v1.2.8 — 06.08.2026 — Удаление чеков администратором

- **Зачем:** кассир мог пробить ошибочные дубли (напр.: 4 чека по 801 с. вместо одного), админу нужно было их убирать.
- **Решение:** в окне редактирования чека — кнопка «🗑 Удалить чек» с подтверждением.
- **Логика удаления (бэкенд сам выбирает режим):**
  - битый/PENDING-чек (`c1_synced=false` или ref начинается с `PENDING:`) — его нет в 1С, удаляется физически (items + шапка);

- **Аудит:** каждое удаление логируется в `pos_receipt_edits` (before-снимок + кто/когда).
- **API:** новый роут `POST ?action=delete-receipt` (`{ref, deletedBy, note}`), требует `X-Provision-Secret`.

## v1.2.7 — 06.08.2026 — Мгновенное закрытие смены (синхронизация с 1С — фоном)

- **Проблема:** закрытие смены висело со спиннером «Смена закрывается…» до ~45 секунд (жалобы с Айни и Сити-Молла).
- **Причина:** закрытие синхронно ждало всю цепочку запросов к внешнему 1С (сервер по HTTP, ~1.5с/запрос): закрытие документа смены + формирование ОРП + простановка ссылки ОРП в КАЖДЫЙ чек отдельным запросом (1 чек = 1 запрос).
- **Решение:** закрытие разбито на две фазы. Фаза 1 (`closeShiftFast`) — только Supabase (статус + суточный отчёт с выручкой), возвращается фронту мгновенно. Фаза 2 (`closeShift1C`) — 1С-синхронизация, вызывается фоном отдельным запросом `?action=close-shift-1c` (fire-and-forget с фронта), идемпотентна.
- **Ускорение ОРП:** простановка ссылок в чеках теперь параллельная (пачки по 6) вместо последовательной.
- **Статус синхронизации:** смена помечается `c1_sync_status='pending'` при быстром закрытии и `ok`/`close_error` после фоновой синхронизации.

## v1.1.1 — 05.08.2026 — Фикс: новые продажи не попадали в отчёты

- Исправлена причина, по которой сегодняшние продажи не отображались в разделах Обзор / Чеки продаж / Отчёты за день: чек проводился в 1С, но не сохранялся в базе РМК.
